# Crownlands: LOD, чанки и подгрузка большого мира

Исследование: 29 октября 2026 года. Исходники проекта сопоставлены с актуальной документацией Roblox и первичными разборами проектов. Игра не запускалась; параметры сохранённого места и фактическая производительность этим исследованием не измерены. Ниже отдельно указаны факты и предлагаемые решения. Системы LOD/чанков этим документом не считаются реализованными.

## Рекомендация для проекта

Совместить встроенный Instance Streaming, небольшие пространственно связанные модели, LOD статического окружения и отдельное управление активностью игровых систем по зонам. Собственный серверный загрузчик всей карты пока не нужен без подтверждённой проблемы серверной памяти или необходимости бесконечной генерации.

Для работы исключительно с локальным `.rbxl` подходит встроенный streaming плюс собственные упрощённые визуальные модели. Для облачной рабочей копии целесообразен пилот SLIM на статических домах и деревьях. Сохранение в Roblox и Team Create — отдельные условия, которые не выполняются автоматически этим исследованием.

## Что уже есть и чего нет

| Проверено по исходникам | Значение |
|---|---|
| Размер мира | 14 336 × 14 336 studs, около 4 × 4 км |
| Встроенный streaming | Сборщик включает StreamingEnabled; журналы от 20 октября описывают успешную подгрузку деревни |
| Структура зданий и леса | Дома и отдельные деревья — небольшие Model с Atomic; все поселения не объединены в одну Atomic-модель |
| Геометрия леса | По журналу 3066 деревьев; по коду 4 Part на дерево — 12 264 детали на весь лес, а не на каждый клиент |
| Terrain | Строится в редакторе через FillBlock/FillBall; блоки FillBlock 1024 studs относятся к сборке, а не к runtime-загрузке чанков |
| LOD окружения | Явное назначение Model.LevelOfDetail и отдельные LOD-ассеты отсутствуют |
| Настройки streaming | Нет явной конфигурации ModelStreamingBehavior, StreamOutBehavior, StreamingIntegrityMode и радиусов в подготовленных исходниках; действительные значения надо читать из места |
| Локальный декор | Цветы и ветви собираются множеством отдельных Parts; даже без тяжёлых текстур это создаёт накладные расходы |
| NPC | Новый торговец содержит Humanoid; его надо исключить из статических SLIM-групп |

Уже существующий streaming — важная основа. Из наличия больших размеров мира нельзя заключить, что вся карта целиком загружена у каждого игрока или что чанков совсем нет на уровне движка.

## Три разных механизма

**Instance Streaming** управляет присутствием геометрии и связанных Instances у клиента. Он снижает клиентскую память и объём репликации. Не является универсальным выключателем серверной памяти и серверной логики.

**LOD** меняет стоимость визуального представления: вблизи детали, дальше упрощённая модель, ещё дальше силуэт или отсутствие мелкого объекта. LOD не заменяет подгрузку и не должен менять серверные правила попаданий и препятствий.

**Зоны/чанки проекта** дают пространственный индекс для содержимого, генерации, логики NPC, эффектов и очередей создания декора. Простое перемещение объектов в Folder с именем Chunk не запускает загрузку/выгрузку и само по себе не сокращает память.

Основание: [Instance streaming](https://create.roblox.com/docs/workspace/streaming), [Techniques and conversion](https://create.roblox.com/docs/workspace/streaming/techniques).

## Настройка встроенного streaming

Стартовая конфигурация для сравнений, а не обещание оптимальных значений:

| Свойство Workspace | Предложение |
|---|---|
| StreamingEnabled | true |
| ModelStreamingBehavior | Improved |
| StreamOutBehavior | Opportunistic |
| StreamingIntegrityMode | PauseOutsideLoadedArea |
| StreamingMinRadius | 64 — рекомендованная Roblox исходная точка |
| StreamingTargetRadius | Сравнить 512 и 1024; 1024 — рекомендация Roblox, 512 — наш более экономный кандидат |

Эти настройки задаются в Properties Workspace редактора. Меньший радиус не гарантирует отсутствие рывков: он также сокращает запас пространства для подгрузки. При полёте 800 studs/s расстояние 512 studs проходится за 0,64 с. Это геометрическая оценка, не измерение скорости сети; состояние буфера и готовность контента зависят от устройства и движка.

Не увеличивать число replication foci без необходимости. Для телепортов и удалённых точек осмотра предусмотреть отдельную подготовку области через API streaming и корректное ожидание готовности. Не вызывать RequestStreamAroundAsync каждый кадр.

Источник и ограничения радиусов: [Instance streaming](https://create.roblox.com/docs/workspace/streaming).

## Как разделить карту

Предлагаемый пространственный индекс — ячейки **256 × 256 studs**. Это параметр архитектуры Crownlands, не обязательный размер внутренних регионов Roblox. Для сравнения можно оценить 512 × 512.

- Сетка 256 даёт 56 × 56 = 3136 возможных ячеек на нынешнем мире.
- Сетка 512 даёт 28 × 28 = 784 возможные ячейки.
- Создавать/индексировать только непустые ячейки; не заводить тысячи пустых объектов ради сетки.
- Регион хранит идентификаторы и ссылки на небольшие логические модели. Граница сетки не должна разрезать один дом или одну интеракцию.
- Ячейка 256–512 не должна быть одним огромным Atomic Model. Atomic подходит отдельному дому, дереву или небольшому интерактивному набору, которому требуется целостная первичная репликация.
- Большие лесные массивы, городские контейнеры и кварталы не делать Persistent. Такие модели остаются в памяти клиента и не выгружаются.

В документации Roblox ориентир для LOD-моделей — компактные пространственные размеры, примерно до 64 studs по габаритам; это рекомендация группировки, а не жёсткий предел движка. Для больших сооружений нужны небольшие модули, а не один прокси на весь город.

Пример целевой структуры, а не описание уже выполненной миграции:

```text
Workspace
  Map
    Terrain                         # обрабатывает native streaming
    StaticRegions
      Region_x_z                    # Folder / пространственный индекс
        House_01                    # небольшой static Model
        Tree_01                     # небольшой static Model
        WallSegment_01              # отдельный модуль стены
    Gameplay                        # NPC, интеракции и изменяемые объекты

ReplicatedStorage
  WorldManifest                     # компактные описания/идентификаторы
  DecorTemplates                    # небольшой набор повторяемых шаблонов
```

Небольшой набор шаблонов допустим; хранение всех размещённых экземпляров карты в ReplicatedStorage не является оптимизацией клиентской памяти.

## Варианты LOD

### A. Native streaming + SLIM для статического окружения

Современный SLIM автоматически генерирует составные представления моделей и несколько уровней детализации в облаке; движок выбирает представление по ресурсам и дистанции. Работает с Parts и MeshParts, поэтому существующий Parts-блок-аут не требуется сначала целиком переделывать в меши.

Условия: StreamingEnabled, место сохранено в Roblox, включён Team Create. В локальном `.rbxl` без облачной генерации результата SLIM не будет. Модели с Humanoid и изменяемая/анимированная геометрия не подходят для статического SLIM. Торговца, изменяемые двери и эффекты надо отделить от статических домов. У самого SLIM пороги переходов выбирает движок; диапазоны собственного LOD нельзя выдавать за его настройки.

Первый пилот: один типовой дом, один участок стены и несколько типов деревьев. Проверить статусы генерации через SLIM TranscoderStatus в редакторе. Наличие LevelOfDetail=SLIM без готового транскодирования не доказывает, что оптимизация работает. Визуальные переходы и реальный эффект требуют последующей runtime-проверки.

Источник: [SLIM](https://create.roblox.com/docs/workspace/streaming/slim).

### B. Native streaming + собственные LOD визуального декора

Подходит текущему локальному режиму. Сервер хранит авторитетный мир и коллизии; клиент управляет ограниченным декоративным слоем. Нужны компактный манифест размещений и небольшой набор шаблонов, а не полные копии всех трёх версий карты.

Пример стартовых диапазонов для пилота, не универсальный норматив:

| Дистанция | Предлагаемый вид |
|---|---|
| 0–160 studs | Близкие детали, цветы пучками, подробный силуэт дерева/дома |
| 160–512 | Упрощённые повторяемые модели; без мелких ветвей и отдельных лепестков |
| 512–1536 | Очень дешёвые силуэты важных зданий и групп леса; мелкого декора нет |
| Дальше | Только значимые ориентиры при необходимости; Terrain остаётся под управлением движка |

Для дерева LOD1 можно сделать одной-двумя оптимизированными повторяемыми моделями, для дальнего леса — силуэтом небольшой группы. Не объединять всю лесную область в одну огромную модель.

Требования к менеджеру: пространственный поиск по ячейкам, проверки по смене ячейки или раз в 0,2–0,5 с, разные пороги входа/выхода, очередь создания/удаления с ограничением времени кадра, очистка обработчиков и ограниченные пулы. Значения периодов — проектные кандидаты для измерения. Смена ячейки не должна вызывать массовый Clone/Destroy за один кадр.

При собственном визуальном слое нельзя обещать, что native streaming автоматически выгрузит все локальные копии: их жизненным циклом управляет сам менеджер. И нельзя локально удалять серверную геометрию как основной способ LOD — она может снова прийти через репликацию.

Предупреждения о client-only копиях: [Techniques and conversion](https://create.roblox.com/docs/workspace/streaming/techniques). Снижение частоты и распределение тяжёлой работы: [Improve performance](https://create.roblox.com/docs/performance-optimization/improve).

### C. Собственный серверный загрузчик чанков

Оправдан для бесконечного процедурного мира или измеренного дефицита серверной памяти. Для нынешней конечной карты это наиболее дорогой вариант: он затрагивает серверную жизнь NPC, интеракции, столкновения и состояние объектов.

Требуется учитывать объединение областей всех игроков, телепорты, летящие снаряды, существующие ссылки на объекты, повторную загрузку и независимое сохранение состояния. Нельзя выгружать район только потому, что из него вышел один игрок, если там остаются другие игроки или активные игровые объекты. Существующий Bootstrap ожидает TrainingYard уже при запуске: перенос двора в отложенно загружаемый серверный чанк без изменения этой зависимости сломает инициализацию.

Terrain нельзя «переложить по папкам» как обычные Models. Собственная запись/очистка вокселей во время игры — отдельная система с затратами CPU и репликации, а не необходимое условие оптимизации нынешней карты.

Это проектная оценка риска по архитектуре Crownlands. Нативный streaming уже решает клиентскую часть и не требует такой переработки всего сервера.

## Разобранные кейсы

1. **City People Cars SLIM Template.** Официальная демонстрация Roblox с SLIM на объектах мира. Полезна для пилота на зданиях и городском окружении: вместо исчезновения дальней модели остаётся упрощённое представление. Официальная страница не даёт универсального процента ускорения для любой карты. [Описание и ссылка на демо](https://create.roblox.com/docs/workspace/streaming/slim).
2. **Beyond the Dark / Kerr-Newman DSR-14.** Создатели использовали модульные MeshParts, повторяемые материалы и trim sheets. Около 90% архитектуры использовало небольшой набор наборов текстур; часть геометрии объединялась так, чтобы уменьшить число материалов и draw calls. Это кейс организации ассетов, а не доказательство, что сетка чанков сама повышает FPS. Для Crownlands применимы повторяемые дома, стены и материалы. [Разбор авторов](https://create.roblox.com/docs/resources/beyond-the-dark/building-architecture).
3. **The Mystery of Duvall Drive.** Команда повторно использовала анимации деревьев, размещала дорогую анимированную растительность только в наиболее значимой области у дома и упрощала коллизии там, где высокая точность не требовалась. Для нашего леса вывод — дорогие детали рядом с игроком и важными сценами; дешёвые повторяемые варианты на остальной территории. [Разбор авторов](https://create.roblox.com/docs/resources/the-mystery-of-duvall-drive/develop-a-moving-world).

Рекомендации 2026 года важнее старых форумных советов «перенести карту в ReplicatedStorage и менять Parent». Такой подход может сократить работу Workspace, но не устраняет хранение уже реплицированного полного мира на клиенте.

## Проверка результата

До изменения архитектуры нужно различить: лаги редактора, низкий FPS клиента, рывки загрузки и задержки сервера. Они требуют разных исправлений. In-game streaming не является обещанием уменьшить стоимость всей загруженной сцены в редакторе.

Без запуска игры доступны: инвентаризация Models/Parts/теней/коллизий, проверка габаритов и расстояний внутри моделей, аудит настроек Workspace, проверка разделения static/dynamic, анализ кода и тестирование планировщика собственного LOD на заменах API. Подготовленный `tools/audit-map-edit.luau` делает часть этой инвентаризации.

Подтвердить FPS и реальные выгрузки без сессии нельзя. Последующий приёмочный маршрут должен быть одинаков до и после изменения: спавн → город → лес → мост → деревня → возврат, плюс отдельно быстрый полёт. Нужны среднее время кадра и P95/P99, скачки длительности кадров, клиентская память, число клиентских Instances, draw calls, стоимость теней и затраты streaming. Средний FPS сам по себе скрывает рывки.

Часть runtime-диагностики: [Scene Analysis](https://create.roblox.com/docs/performance-optimization/scene-analysis) и [MicroProfiler](https://create.roblox.com/docs/performance-optimization/microprofiler). Scene Analysis по документации предназначен для play/test-сессий; его runtime-результаты сейчас не получены.

## Предлагаемый порядок внедрения

1. Зафиксировать действительные настройки и структуру сохранённой карты; отделить проблему редактора от проблемы клиента/сервера.
2. Настроить native streaming и сравнимые профили; не уменьшать карту и не объединять её в крупные Atomic-контейнеры.
3. Сделать пространственный индекс 256 studs для непустых областей и разнести статическое окружение и игровые объекты.
4. На одном типовом участке сравнить собственный LOD и, если допустима облачная рабочая копия, SLIM. Выбирать по устройствам и результатам пилота.
5. Оптимизировать повторяемые деревья, стены и цветы; после проверки тиражировать решение на весь мир.
6. Отдельно ограничить дальнюю активность NPC/эффектов. Возвращаться к серверной загрузке Terrain/чанков только при обоснованной необходимости.

Не изменены этой работой: runtime-архитектура, сохранённый `.rbxl`, облачные настройки и публикация. Предыдущие правки NPC/полёта и профили графики остаются отдельными выполненными изменениями.
